# 测试用例文档

> 这里是「测什么」的清单：**一个设置页一份文档，一条场景一段话**，先讲清用户会遇到什么，再挂对应用例。
> `docs/e2e-testing.md` 是「怎么写」的指南，用例代码在 `e2e/`。

## 为什么要这份文档

- 「页面上填了、实际没保存成功」这类问题，根因往往在**场景组合**（跨字段、跨页、跨时机），而按控件逐个字段铺用例铺不出它们——必须先把场景列全、评审过，再写代码。
- 不读代码的人（比如项目 owner）只能审文档。所以场景清单要独立于代码存在，作为评审对象；也因此按页面拆开写，而不是一张大表。
- 缺口要被看见：没有哪条场景被漏掉，往往不是判断出来的，而是列出来的。

## 什么时候算「覆盖完」

单个控件有值落盘、能回显，只算**成功路径**。一个功能真正被覆盖，至少要在这几类里各有判断：

| 场景类型 | 问自己 |
|---|---|
| 成功路径 | 改完真的落盘了吗？重进页面/重启应用还在吗？ |
| 失败路径 | 后端拒绝时，用户看得到原因吗？坏值会不会同时被写进去？ |
| 时机 | 防抖窗口内离开、连续改、保存中又改，会怎样？ |
| 跨页耦合 | 改 A 页会不会让 B 页的行为变？A 页的改动会不会让 B 页的入口失效？ |
| 重启持久化 | 关掉应用再开，还在吗？ |
| 边界 | 空值、非法值、删空、清空，这些分支怎么走？ |
| 外部依赖 | 依赖外网/真实模型/系统浏览器的行为，只能人工验 |

范围只覆盖**跨进程链路**（界面 → IPC → 主进程 → 数据库/配置文件），纯函数与服务层逻辑归 vitest，不在这里重复。

## 用例 ID 与状态

- 每份页面文档顶部先声明这一页的用例文件：`` 用例文件：`e2e/xxx.spec.ts` ``。
- ID 形如 `SET-PRX-01`：`SET` = 设置中心，中段 = 页面或范围，末段 = 该范围内的序号。ID 一旦分配就不再复用。
- 每条场景挂一个 ID，文档里只有两种写法：

```markdown
- 用例：**[SET-PRX-01]** 切到自定义并填写代理地址与直连规则后落盘，重进页面仍回显
- 编号：**[SET-PRX-03]**（未覆盖）产品规则还没定：切回「跟随系统」时地址是保留还是清掉
```

- 同一个 ID 还要出现在 spec 的 `test()` 标题里，写成 `test('[SET-PRX-01] 场景描述', ...)`。
- 本文件也登记缺口，但只登记**跨页面、挂不到任何单一页面上**的机制性缺口（见文末），所以它只允许出现「编号」行，不允许出现「用例」行。
- 缺口只有两种，都要求 ID **不出现在任何 spec 里**：

| 状态 | 含义 |
|---|---|
| `未覆盖` | 值得自动化但还没做（多半是产品规则没定，或链路太长还没拆） |
| `手动` | 依赖外网/真实模型/系统浏览器，不适合 e2e |

## 校验

```bash
yarn test:cases:check   # 文档与用例双向比对（已串进 yarn test:e2e）
```

跑通时会按页打印概览（每页自动化几条、缺口是哪几个）。**概览不手写进文档**——手写的概览迟早和清单对不上。

报错只有两种，都指向「有人只改了一边」：

- **未翻译**：文档标了 `自动化`（`- 用例：`），但该页 spec 里找不到这个 ID（或者写在别的文件里）。
- **未登记**：spec 里出现了这个 ID，但文档没把它登记为 `自动化`（要么没这条，要么标的是缺口）。

所以删用例时要同步删文档行（不能留一条永远红的 `自动化`），改文件名时要同步改文档顶部的「用例文件」。

## 跨页面的机制性缺口

- 编号：**[SET-AUTO-02]**（未覆盖）保存还没发出就关窗/退出应用：改动是随卸载时的 flush 一起提交的，若进程先退出，flush 里的 IPC 可能来不及往返。要自动化就得让用例真正关窗，属于进程生命周期场景，暂缓。
- 编号：**[SET-AUTO-03]**（未覆盖）保存失败后又立刻切走：此时页面上还挂着失败提示，用户直接离开会看到提示一闪而过，回来只看得到旧值。要不要在离开时拦一下（或让提示跟随到新页面）还没定。
